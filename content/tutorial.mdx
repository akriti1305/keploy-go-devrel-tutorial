# Zero-to-Test: API Testing with Keploy, Go, and MongoDB

A hands-on tutorial for developers who have never used Keploy. We will run a real Go URL-shortener service, record its behavior with Keploy, and replay those recordings as automated tests — without writing a single assertion by hand.

---

## What is Keploy?

Most testing tools ask you to write tests. Keploy takes the opposite approach: **it watches your running application and writes the tests for you.**

Here is the core idea in one sentence: Keploy intercepts every network call your service makes — incoming HTTP requests, outgoing database queries, external API calls — records them as YAML files, and then replays those recordings later to verify your app still behaves exactly the same way.

This is called **record-and-replay testing**, and it has a major advantage for integration testing: because Keploy captures real database calls, it can mock the database perfectly during test replay. Your application thinks it is talking to MongoDB; Keploy is quietly serving the pre-recorded responses. No test database, no seeding scripts, no cleanup.

**Why is this valuable for a Go developer?**

- No test boilerplate — you do not write `assert.Equal(t, expected, actual)` for every field
- Real request/response pairs captured from actual traffic, not invented by a developer
- Mocks are auto-generated, not manually maintained
- Tests run fast because there is no live database needed during replay
- CI-ready out of the box

## What We Are Building

We will use the official **Keploy `gin-mongo` sample app** — a URL shortener service written in Go using the [Gin](https://gin-gonic.com/) web framework and [MongoDB](https://www.mongodb.com/) as the database.

The service exposes two endpoints:

| Method | Path | What it does |
|--------|------|--------------|
| `POST` | `/url` | Accepts a long URL, stores it, returns a short hash |
| `GET` | `/:hash` | Looks up the hash in MongoDB, redirects to the original URL |

After this tutorial you will have:
- A working Go service running in Docker
- Real API test cases generated by Keploy
- Auto-generated MongoDB mocks
- A passing test run (no live database required)

## Prerequisites

Before starting, make sure you have the following installed on your machine:

| Tool | Minimum Version | Why it is needed |
|------|----------------|-----------------|
| Docker | 20.10+ | Runs the app and MongoDB in containers |
| Docker Compose | v2 | Orchestrates multi-container setup |
| Go | 1.21+ | Needed only if you want to build/run natively |
| curl | Any | Makes HTTP requests during recording |
| Keploy CLI | Latest | The star of the show |

<Callout type="info" title="Platform Architecture & eBPF Requirements">
Keploy's transparent traffic interception relies on **Linux kernel eBPF** (extended Berkeley Packet Filter) to capture socket syscalls without modifying application code.

- **On Linux:** Keploy runs natively on the host (`sudo -E keploy record -c "./my-app"`).
- **On Windows & macOS:** Because eBPF is a Linux kernel feature, native execution directly on the Windows host is not supported by the open-source CLI. Running `keploy record -c "./my-app"` directly in Windows PowerShell produces:
  ```
  ERROR failed to validate flags: running an application directly on windows/amd64 is not supported by this build of Keploy, which intercepts traffic with eBPF (Linux only).
  ```
- **The Cross-Platform Standard:** To record and replay services on Windows or macOS, Keploy uses **Docker containers** on a shared bridge network (`keploy-network`) or a **WSL2** Linux environment.

This tutorial teaches the official Docker-based workflow, which works consistently across Linux, macOS, and Windows with Docker Desktop or WSL2.
</Callout>

## Understanding the App

Here is the application structure you are working with:

```
samples-go/gin-mongo/
├── main.go           # Server setup: connects to MongoDB, registers routes
├── handler.go        # Route handlers: putURL (POST) and getURL (GET)
├── Dockerfile        # Two-stage Go build → Alpine runtime image
├── docker-compose.yaml # App + MongoDB services on keploy-network
└── keploy/           # Generated by Keploy after recording
    └── test-set-0/
        ├── tests/
        │   ├── test-1.yaml   # Recorded POST /url test case
        │   └── test-2.yaml   # Recorded GET /:hash test case
        └── mocks.yaml        # Captured MongoDB wire-protocol calls
```

A quick look at the key code paths:

**`main.go`** — sets up the router:
```go
r := gin.Default()
r.GET("/:param", getURL)
r.POST("/url", putURL)
r.Run(":" + port)
```

**`handler.go`** — the `putURL` handler hashes the URL using SHA-256 + Base58, then upserts it into MongoDB:
```go
func putURL(c *gin.Context) {
    // SHA-256 hash the long URL, take first 8 Base58 chars as the short key
    // Store {_id: shortKey, url: originalURL} in MongoDB
    // Return { "ts": unixNano, "url": "http://localhost:8080/<shortKey>" }
}
```

The hash function is deterministic — the same input URL always generates the same short key. That is why `https://google.com` always becomes `Lhr4BWAi`.

<Step number={3} title="Set Up the Docker Network">

Keploy needs a dedicated Docker network to intercept traffic between your application container and MongoDB. This is the `keploy-network` that both services must share.

<CodeBlock
  code="docker network create keploy-network"
  language="bash"
/>

<Callout type="info" title="Why a custom network?">
Docker containers on the same custom bridge network can resolve each other by container name. The Go app connects to MongoDB using `mongoDb:27017` (container name as hostname). If both containers are on `keploy-network`, this name resolves correctly. Keploy also uses this shared network context to intercept the TCP traffic between the two containers.
</Callout>

</Step>

---

<Step number={4} title="Start MongoDB">

Spin up a MongoDB container attached to `keploy-network`:

<CodeBlock
  code="docker run -p 27017:27017 -d --network keploy-network --name mongoDb mongo"
  language="bash"
/>

Verify it is running:

<CodeBlock code="docker ps | grep mongoDb" language="bash" />

Expected output (abbreviated):
```
<container-id>   mongo   ...   27017/tcp   mongoDb
```

<Callout type="tip">
The container name `mongoDb` is important — it must match the hostname the Go app uses in `main.go`:
```go
client, err := New("mongoDb:27017", dbName)
```
If you use a different container name, the app will fail to connect.
</Callout>

</Step>

<Step number={6} title="Record Test Cases">

This is where Keploy comes alive. Run this command to start the app **under Keploy's watch**:

<CodeBlock
  code={'keploy record -c "docker run -p 8080:8080 --name MongoApp --network keploy-network gin-app:1.0"'}
  language="bash"
/>

Let us break down every flag:

| Flag | Value | Purpose |
|------|-------|---------|
| `record` | — | Tell Keploy to enter recording mode |
| `-c` | `"docker run …"` | The command Keploy should launch (your app) |
| `--name MongoApp` | — | Container name — Keploy uses this to hook into the container's network namespace |
| `--network keploy-network` | — | Puts the app on the same network as MongoDB |

<Callout type="info" title="What is Keploy doing right now?">
Keploy launched your container, then injected an **eBPF probe** (or a user-space proxy on macOS/Windows) to sit in front of every network socket the app opens. From this moment on:

- Every **incoming HTTP request** is intercepted and stored
- Every **outgoing MongoDB call** is intercepted and stored

Your app is completely unaware of this. It is reading from and writing to what it believes is a real MongoDB connection — but Keploy is the silent middleman recording every byte.
</Callout>

You should see output like:
```
🐰 Keploy: Starting recording...
🐰 Keploy: Waiting for traffic on port 8080...
```

**Leave this terminal open.** Keploy is actively listening. Do not press Ctrl+C yet.

</Step>

<Step number={7} title="Make API Calls to Generate Test Cases">

Open a **new terminal** and make two API calls. These become your test cases.

**Call 1 — Create a shortened URL:**

<CodeBlock
  code={`curl --request POST \\
  --url http://localhost:8080/url \\
  --header 'content-type: application/json' \\
  --data '{"url": "https://google.com"}'`}
  language="bash"
/>

Expected response:
```json
{"ts": 1718943885198315028, "url": "http://localhost:8080/Lhr4BWAi"}
```

The `ts` field is the current Unix timestamp in nanoseconds. The `url` field contains your shortened link. Note the hash `Lhr4BWAi` — this is a deterministic Base58 encoding of the SHA-256 hash of `https://google.com`, so it will always be the same value.

**Call 2 — Follow the shortened URL:**

<CodeBlock
  code="curl -L http://localhost:8080/Lhr4BWAi"
  language="bash"
/>

The `-L` flag tells curl to follow redirects. The server returns a `303 See Other` redirect to `https://google.com`, and curl follows it.

Now go back to your first terminal and press **Ctrl+C** to stop the recording.

<Callout type="success" title="Two tests captured!">
After stopping, Keploy will have written your test cases to disk. Check the `keploy/` folder:

```
keploy/
└── test-set-0/
    ├── tests/
    │   ├── test-1.yaml    ← POST /url — create short link
    │   └── test-2.yaml    ← GET /Lhr4BWAi — follow the redirect
    └── mocks.yaml         ← All MongoDB wire-protocol calls
```
</Callout>

</Step>

## What Keploy Generated

To understand the internal format of Keploy's test suite, let us examine the canonical reference artifacts (`test-1.yaml`, `test-2.yaml`, and `mocks.yaml`) provided in the official sample repository. These files illustrate the exact schema generated during a successful recording run in a containerized Linux environment.

**`test-1.yaml` — the recorded POST request:**
```yaml
version: api.keploy.io/v1beta1
kind: Http
name: test-1
spec:
  req:
    method: POST
    url: http://localhost:8080/url
    header:
      Content-Type: application/json
    body: '{"url": "https://google.com"}'
  resp:
    status_code: 200
    body: '{"ts":1718943885198315028,"url":"http://localhost:8080/Lhr4BWAi"}'
  assertions:
    noise:
      body.ts: []       # ← This field is excluded from comparison
      header.Date: []   # ← HTTP Date header is excluded too
```

Notice the `noise` section. Keploy automatically detected that `body.ts` is a timestamp that changes on every call, so it added it to the noise list — meaning this field will be **ignored during test comparison**. This is one of Keploy's smartest features: it knows which fields are inherently non-deterministic and excludes them automatically.

**`mocks.yaml` — the MongoDB calls:**

This file contains the full MongoDB wire-protocol conversations — the exact bytes that went between the Go driver and MongoDB. During test replay, Keploy serves these pre-recorded responses, so MongoDB does not need to be running at all.

---

<Step number={8} title="Run the Tests">

With the test cases recorded, you can now replay them against a fresh instance of your app. Keploy will start the app, intercept its outgoing database calls, serve the pre-recorded MongoDB responses, make the original HTTP requests, and compare the responses.

**First, clean up the old container:**

<CodeBlock
  code="docker rm -f MongoApp"
  language="bash"
/>

**Then run the tests:**

<CodeBlock
  code={'keploy test -c "docker run -p 8080:8080 --name MongoApp --network keploy-network gin-app:1.0" --delay 10'}
  language="bash"
/>

The `--delay 10` flag tells Keploy to wait 10 seconds after starting the app before firing the test requests. This gives the app time to boot, connect, and be ready to serve.

Expected output:
```
🐰 Keploy: Running test-set-0 (2 tests)...
✅ Test 1 PASSED — POST /url
✅ Test 2 PASSED — GET /Lhr4BWAi
─────────────────────────
Tests run: 2 | Passed: 2 | Failed: 0
```

<Callout type="success" title="No MongoDB required!">
Did you notice? You did not start MongoDB this time. Keploy intercepted every outgoing database call and served the responses from `mocks.yaml`. Your app never knew the difference. This is the power of Keploy's dependency virtualization.
</Callout>

</Step>

## Understanding Noise Fields

One thing that trips up first-time Keploy users: the `ts` (timestamp) field in the response.

During recording, the actual `ts` value was `1718943885198315028`. During replay, the app will generate a different timestamp. If Keploy compared this field literally, the test would always fail.

Keploy handles this automatically — when it first detects that the `ts` field changed between two runs, it adds it to the `noise` list in the test YAML:

```yaml
assertions:
  noise:
    body.ts: []
```

But if you ever see failures because of timestamp fields that are **not** automatically detected as noisy, you can add them manually. Just edit the YAML and add the field path under `noise`.

## Troubleshooting

<Callout type="warning" title="'MongoApp' container already exists">
If you see `Error: The container name "/MongoApp" is already in use`, run:
```bash
docker rm -f MongoApp
```
Then retry the command.
</Callout>

<Callout type="warning" title="Connection refused on port 8080">
Make sure no other process is using port 8080. Check with:
```bash
# On Linux/macOS
lsof -i :8080
# On Windows
netstat -ano | findstr 8080
```
</Callout>

<Callout type="warning" title="keploy: command not found">
Keploy was installed to `/usr/local/bin`. If it is not found, add this to your shell profile:
```bash
export PATH=$PATH:/usr/local/bin
```
Then reload with `source ~/.bashrc` (or `~/.zshrc`).
</Callout>

<Callout type="info" title="Tests failing with timestamp mismatch?">
If you see a failure like `body.ts does not match`, manually add `body.ts` to the noise field in your test YAML:
```yaml
assertions:
  noise:
    body.ts: []
    header.Date: []
```
</Callout>

<Callout type="info" title="Running on Windows or macOS?">
Keploy's core interception engine relies on Linux kernel eBPF (extended Berkeley Packet Filter) to transparently capture network syscalls.

If you attempt to run `keploy record -c "./my-app"` directly on native Windows PowerShell or cmd, the open-source CLI will exit with:
```
ERROR failed to validate flags: running an application directly on windows/amd64 is not supported by this build of Keploy, which intercepts traffic with eBPF (Linux only).
```
To run Keploy on Windows:
1. **Docker workflow (recommended):** Use `keploy record -c "docker run ..."` as shown in this tutorial.
2. **WSL2 workflow:** Install Ubuntu in WSL2 (`wsl --install -d Ubuntu`), run Docker Desktop with the WSL2 backend enabled, and execute Keploy directly within the Linux terminal.

On macOS, Docker Desktop 4.25.2+ is similarly required to provide the Linux VM backend for eBPF.
</Callout>

## Conclusion

This hands-on walkthrough illustrates what makes Keploy genuinely different from traditional testing tools:

1. **Zero test assertions to write:** Keploy captures expected service behavior directly from live network traffic.
2. **Zero hand-written mocks to maintain:** Keploy captures downstream database wire-protocol interactions and replays them automatically.
3. **CI-ready regression testing:** The `keploy/` directory can be committed to Git and executed in any Linux/Docker CI pipeline.

The real magic is the workflow that Keploy enables:

> Record once in staging → commit the YAML files → replay in CI forever

Every time you change code, `keploy test` catches regressions without you writing a single extra line of test code.

**What to explore next:**

- Add Keploy to a **GitHub Actions** CI workflow using `keploy test` in a pipeline step
